# 多跳交易代码实现

本文对应课程 2.3，说明如何把 BFS、DFS 的图搜索思想落到当前项目的 SQL 与 Go 实现中。

## 1. 把池子数据抽象成图

- Token 是顶点。
- 流动性池是连接两个 Token 的边。
- `reserve0`、`reserve1`、`fee_rate`、`liquidity_usd` 是边的属性。
- 搜索目标是在限定跳数内，从 `tokenIn` 找到 `tokenOut` 的可报价路径。

数据表位于 `lesson2.2/backend/.sql/schema.sql`，核心表是 `token_liquidity_pools`。

## 2. BFS、DFS 与项目方案

### BFS

BFS 按跳数逐层扩展。先检查单跳，再检查两跳、三跳，因此适合优先寻找跳数较少的路径。通用实现通常需要：

- 邻接表：`token -> pools`
- 队列：保存当前 Token、路径和已使用池子
- `visited` 或路径内去重
- `maxHops`：限制最大跳数

### DFS

DFS 沿一条路径继续向下搜索，抵达目标或最大深度后回溯。它适合枚举固定深度内的所有简单路径，但必须避免环路和候选爆炸。

### 当前项目：固定深度 SQL + 应用层

项目没有实现通用 BFS/DFS。当前实现把搜索深度展开成 SQL：

- 单跳：`FindDirectRoute`
- 两跳：`FindTwoHopRoute`
- 三跳：`FindThreeHopRoute`

SQL 负责连接池子、过滤链与活跃状态、应用最小流动性阈值。Go 负责组装 `Route`、逐跳模拟、评分和排序。这种方案容易理解，查询规模也可控，但扩展到任意跳数时需要新增 SQL 或改为通用图搜索。

## 3. 两跳路径如何生成

`FindTwoHopRoute` 位于 `lesson2.2/backend/api/bot.go`。

第一层 CTE 从 `tokenIn` 出发，使用 `CASE` 得到中间代币：

```sql
CASE
  WHEN token0_address = ? THEN token1_address
  ELSE token0_address
END AS intermediate_token
```

第二层把中间代币与包含 `tokenOut` 的池子连接起来。查询同时使用以下条件剪枝：

- `chain_id` 相同
- `is_active = 1`
- 两个池子的 `liquidity_usd` 都高于 `minLiquidity`
- 结果按平均流动性排序并限制数量

每一行查询结果会被组装为：

```go
Route{
    Pools:        []Pool{pool1, pool2},
    TokenPath:    []string{tokenIn, intermediateToken, tokenOut},
    TotalFee:     1 - (1-pool1.FeeRate)*(1-pool2.FeeRate),
    AvgLiquidity: avgLiquidity,
}
```

## 4. 三跳路径如何生成

`FindThreeHopRoute` 位于 `lesson2.2/backend/api/routing.go`。

它使用两个 CTE：

1. `first_hop` 找到第一层中间代币。
2. `second_hop` 连接第二个池子并得到第二层中间代币。
3. 最外层查询连接第三个池子到 `tokenOut`。

查询结果限制为 10 条，并按三个池子的平均流动性排序。`FindBestRoute` 只有在没有候选，或两跳候选少于 3 条时，才尝试三跳搜索。

## 5. 逐跳模拟

`SimulateSwap` 位于 `lesson2.2/backend/api/routing.go`。它把上一跳输出作为下一跳输入：

```go
currentAmount := new(big.Int).Set(amountIn)

for i, pool := range route.Pools {
    // 根据 TokenPath[i] 判断 reserveIn 和 reserveOut 的方向
    currentAmount = CalculateOutputAmount(
        currentAmount,
        reserveIn,
        reserveOut,
        pool.FeeRate,
    )
}
```

单跳输出使用恒定乘积公式：

```text
amountInWithFee = amountIn × (1 - feeRate)

amountOut = reserveOut × amountInWithFee
            ──────────────────────────
            reserveIn + amountInWithFee
```

金额使用 `big.Int`，避免普通整数无法容纳链上数量。

## 6. 路由评分

`CalculateRouteScore` 使用三个维度：

- 流动性得分 40%：以路径中的最小流动性作为瓶颈。
- 手续费得分 30%：总手续费越低，得分越高。
- 价格得分 30%：比较模拟输出和简化理论输出。

最终结果按 `TotalScore` 降序排序。该评分是课程项目中的启发式规则，生产系统通常会直接优先比较可执行的最终输出，并加入 gas、失败率、报价时效和价格限制。

## 7. HTTP 调用链

`POST /api/v1/routes/quote` 的调用顺序如下：

```text
GetMultiHopQuote
  -> FindBestRoute
      -> FindDirectRoute
      -> FindTwoHopRoute
      -> FindThreeHopRoute（按条件回退）
      -> CalculateRouteScore
          -> SimulateSwap
  -> 返回 best_route、amount_out 和候选路径
```

路由注册位于 `lesson2.2/backend/api/routes.go`，请求与响应结构位于 `lesson2.2/backend/api/handlers.go`。

## 8. 本地练习

在 `lesson2.2/backend` 目录启动服务：

```bash
go run main.go -config ./config.yaml
```

请求示例：

```bash
curl -X POST http://localhost:8080/api/v1/routes/quote \
  -H 'Content-Type: application/json' \
  -d '{
    "chain_id": 1,
    "token_in": "0xTokenA",
    "token_out": "0xTokenC",
    "amount_in": "1000000000000000000",
    "min_liquidity": 10000
  }'
```

建议覆盖以下测试场景：

1. 有高流动性直连池。
2. 没有直连池，但存在两跳路径。
3. 两跳候选不足，需要三跳回退。
4. 某一跳储备为 0 或格式无效。
5. 调整交易金额后，最优路径发生变化。

## 9. 继续扩展

如果要改为通用 BFS/DFS，可以先把活跃池加载成邻接表，再增加 `maxHops`、路径内去重和候选上限。完成路径枚举后，仍然复用 `SimulateSwap` 与评分逻辑。进一步可加入 gas 成本、缓存过期、池状态区块高度和执行端 `amountOutMin`。
